# CDN-first runtime

A runnable Vite app demonstrates a two-bundle CDN runtime. The React family always loads from same-origin combined builds, and the Tonic UI family loads as one bundled entry from public esm.sh, with the same-origin Tonic bundle if CDN loading fails. It does not use Module Federation or Wujie. The hidden loader frame isolates each import-map realm while the visible inspector remains mounted.

From the app directory in a checkout with workspace dependencies installed:

```bash
npm run dev
```

Open `http://127.0.0.1:4173/`. This command builds all runtime variants into the app's `dist/` directory, then serves the generated HTML and modules through Vite Preview. `npm run build` produces the same static files without starting a server. If you use the app outside this monorepo, its `package.json` declares everything needed for a normal package install.

## How the Vite setup works

The following steps apply to your application. The inspector above is a verification tool; its shell, hidden frame, and five build modes are not required in your app.

### 1. Externalize shared runtime imports

Keep React and Tonic UI out of the application bundle. In your app's `vite.config.js`, add the external rule to your existing configuration:

```js
import react from '@vitejs/plugin-react';
import { defineConfig } from 'vite';

export default defineConfig({
  plugins: [react({ jsxRuntime: 'automatic' })],
  build: {
    target: 'es2022',
    rollupOptions: {
      external: id =>
        /^(react|react-dom)(\/|$)/.test(id) ||
        id === '@tonic-ui/react',
    },
  },
});
```

Continue to use normal imports and JSX in your app:

```jsx
import { createRoot } from 'react-dom/client';
import { Button, TonicProvider } from '@tonic-ui/react';

export function mount(element) {
  createRoot(element).render(
    <TonicProvider>
      <Button>Application button</Button>
    </TonicProvider>
  );
}
```

If your existing JSX configuration uses Emotion, keep that configuration. Only externalize Emotion when you also provide its import-map entries. In this model, Emotion used by Tonic UI is bundled inside the Tonic entry.

### 2. Publish the shared runtime files

Host the React runtime files with your static assets. The [reference React entry](https://github.com/trendmicro-frontend/tonic-ui/blob/main/packages/react-docs/demos/cdn-runtime/entries/react.js) combines React, React DOM client, and the production JSX runtime. The [React DOM root entry](https://github.com/trendmicro-frontend/tonic-ui/blob/main/packages/react-docs/demos/cdn-runtime/entries/react-dom.js) keeps `react` external.

These are separate files because `react` and `react-dom` both have default-import consumers, but one ESM module can expose only one `default`. Both files must use the same React version. The React DOM root file imports the combined file through the import map, rather than bundling a second React copy.

For Tonic UI, use a versioned esm.sh URL:

```text
https://esm.sh/@tonic-ui/react@3.0.0-alpha.1?standalone&external=react,react-dom&target=es2022
```

`standalone` bundles Emotion and ordinary Tonic dependencies into the Tonic implementation. React remains external and resolves to the same runtime used by your app. An esm.sh entry URL can load a wrapper plus its implementation; a bundled implementation does not guarantee one HTTP request.

If you need a same-origin fallback, publish a local Tonic bundle too. Bundle `@tonic-ui/react` and its dependencies, but keep the React family external. The [reference Tonic entry](https://github.com/trendmicro-frontend/tonic-ui/blob/main/packages/react-docs/demos/cdn-runtime/entries/tonic.js) and [Vite configuration](https://github.com/trendmicro-frontend/tonic-ui/blob/main/packages/react-docs/demos/cdn-runtime/vite.config.mjs) show this boundary. Serve every generated asset and use its actual versioned URL in your deployment.

### 3. Install the import map before loading your app

Your deployment supplies the URLs for the shared runtime. This example uses readable asset names; replace them with the URLs produced by your runtime build:

```html
<script type="importmap">
{
  "imports": {
    "react": "/runtime/react-19.2.7.js",
    "react-dom/client": "/runtime/react-19.2.7.js",
    "react/jsx-runtime": "/runtime/react-19.2.7.js",
    "react-dom": "/runtime/react-dom-19.2.7.js",
    "@tonic-ui/react": "https://esm.sh/@tonic-ui/react@3.0.0-alpha.1?standalone&external=react,react-dom&target=es2022"
  }
}
</script>
<script type="module" src="/assets/app.js"></script>
```

Use the actual application entry generated by Vite instead of `/assets/app.js`. Install the map before any application import or module preload that uses these specifiers. Vite's normal development server can continue to resolve dependencies from `node_modules`; this map describes the deployed production build, not a development JSX runtime.

### 4. Handle CDN failure before mounting

If you need fallback, replace the static import map and static app script above with a bootstrap loader. The loader must:

1. Choose the CDN or local Tonic URL before installing the map.
2. Install one import map containing the React entries and the selected Tonic entry.
3. Probe React first, then Tonic, before dynamically importing the application entry.
4. If the Tonic CDN import rejects or exceeds your loading budget, reload into a fresh document with a local-source flag.
5. On the next load, map Tonic to the local bundle and mount the same application entry.

Do not replace an import-map target after imports have started. Native imports cannot be cancelled or safely rebound in the current realm. Do not treat a local bundle, application, CSS, or mount error as a CDN failure; report it instead of entering a reload loop.

The [reference bootstrap](https://github.com/trendmicro-frontend/tonic-ui/blob/main/packages/react-docs/demos/cdn-runtime/public/bootstrap.js) implements this sequence with an eight-second CDN budget. Its scenario injection and parent-frame messages belong to the inspector, not your application. You can reload your application document; a hidden frame is only needed when another UI must remain mounted.

The inspector retains the failed CDN result across its reload and displays the local result immediately below it:

```text
✔ react: local
✘ tonic: cdn (failed)
✔ tonic: local
```

`✔` (U+2714) and `✘` (U+2718) are Unicode characters, not ASCII.

### 5. Use self-hosted esm.sh when required

For an internal registry or a network without access to public CDNs, configure a self-hosted esm.sh instance to resolve the required packages. Registry access and credentials belong on that server, not in browser code.

Point the import map at your instance and use the package name and exact version published to your registry. Keep the same `standalone`, `external=react,react-dom`, and `target=es2022` parameters. Verify registry resolution, browser access, CORS, and your application's CSP before deployment. Changing the host alone does not configure private-registry access.

The server builds and caches the ESM bundle from the published package; no separate `-all` package or UMD artifact is required for this flow. If you instead serve raw package files through jsDelivr, unpkg, or a static file host, you must publish the single-file ESM artifact yourself.

Pin runtime versions and use stable URLs. Applications using the same runtime URLs can reuse browser caches; applications in the same document also share the same module instance. Separate documents have separate JavaScript instances even when they use identical URLs.


## Limitations

The failure presets use an intentionally missing same-origin module. They verify rejection and family fallback, but they do not simulate an esm.sh outage. To test an actual outage, disable the browser cache and block the relevant CDN requests in DevTools.

Cold esm.sh builds can exceed the eight-second loading budget. Fixed root package versions also do not pin every transitive dependency. This example covers startup loading only; it does not cover SSR, later lazy imports, or arbitrary runtime exceptions.
