# CDN with local fallback

Load React and Tonic UI from a CDN first, with automatic fallback to same-origin
runtime files if a CDN import fails or times out during startup. Here, **local**
means assets served from your application's origin, not files on the user's computer.

Start with [CDN setup](../cdn-setup/) for package installation, JSX, the
Provider, and the runtime bootstrap. This page follows
[`examples/cdn-with-fallback`](https://github.com/trendmicro-frontend/tonic-ui/tree/main/examples/cdn-with-fallback)
to add local runtime files and the generated manifest; it does not repeat the
basic setup.

## Try the demo

The demo is the runtime inspector: a visible control shell and a hidden runtime
frame that the bootstrap discards and reloads when a scenario or fallback runs.
Choose a scenario in the dropdown, wait for the selected sources to update, and
read the load log. Click **Retry** to start that scenario again.

| Scenario | Expected result |
| :--- | :--- |
| CDN-first (all families via CDN) | Each family uses the CDN when its probe succeeds and falls back to local when it does not. |
| React + React DOM fail | React and React DOM use same-origin files. Tonic UI stays on the CDN if its CDN is available. |
| Tonic UI bundled entry fails | Tonic UI uses same-origin files. React stays on the CDN if its CDN is available. |
| All CDN families fail | Every family falls back to same-origin files. |
| No Tonic UI CDN configuration | Tonic UI uses same-origin files with no CDN entry at all. React stays on the CDN if available. |
| Use local for all groups | Every family uses same-origin files, with no runtime CDN requests. |

{render('./usage')}

The **runtime-manifest.json** section below the log shows the manifest file the
bootstrap reads: package versions, the CDN and local sources of each family,
the application assets, and the generated Emotion mappings. Use it to see
exactly which URLs a load resolves to.

The demo selects its runtime through the scenario dropdown. Open the demo URL
directly with `?scenario=all-local` to start in local-only mode. To run the
inspector separately, use `npm run dev:inspector` from
[`examples/cdn-with-fallback`](https://github.com/trendmicro-frontend/tonic-ui/tree/main/examples/cdn-with-fallback).

The inspector is a build option of that example, enabled only with the
`--inspector` flag (`npm run build:inspector`, `npm run dev:inspector`); the
default build contains only the reference application. The two products share
the runtime entries, the development plugin, and the bootstrap in
[`examples/cdn-shared`](https://github.com/trendmicro-frontend/tonic-ui/tree/main/examples/cdn-shared);
the inspector adds the control shell, the scenario presets, and a disposable
runtime frame. There is one copy of the shared machinery, so the two products
cannot drift.

## Example app

With workspace dependencies installed and the sibling Tonic UI packages built, run
these commands from the repository root:

```bash
cd examples/cdn-with-fallback
npm run dev
```

Open the URL printed by Vite. You should see **Demo app**. Startup may reload
the document when a CDN family fails; the application mounts after runtime
selection completes. The Demo app renders the generated manifest under the
demo so you can inspect the exact runtime it started with.

Try these checks in the example app URL printed by Vite, not in the demo on
this page:

1. Add `?__local=react,react-dom,tonic-ui` to the URL. The application should
   look the same, with no runtime CDN requests.
2. Edit the text in `src/app.jsx`. Vite should reload the application. This
   example uses page reloads, not React Fast Refresh, with its production
   vendor runtimes.
3. Remove `__local` and `__failed` from the URL to try the CDN again.

`npm run dev` builds the local runtime files and manifest before starting
Vite. As in the basic example, both development and production run the
application on the selected CDN or local runtime rather than on Vite's
optimized copies of the shared packages.

## Configure your application

Use [`cdn-with-fallback`](https://github.com/trendmicro-frontend/tonic-ui/tree/main/examples/cdn-with-fallback)
as the starting point. Relative to [CDN setup](../cdn-setup/) it adds three
things: local runtime files for each family, a manifest that names both CDN
and local sources, and the generated Emotion mappings. The manifest has three
groups (`react`, `react-dom`, `tonic-ui`), one per npm package, so a failing
package falls back on its own without disturbing the others.

### Local runtime entries

[`entries.mjs`](https://github.com/trendmicro-frontend/tonic-ui/tree/main/examples/cdn-with-fallback/entries.mjs)
lists the entry files the build compiles. Each family builds into the same
shape its CDN candidate serves:

| Build | Entry | External imports |
| :--- | :--- | :--- |
| `react` | `entries/react.js`: React, React DOM client, JSX runtimes | None |
| `react-dom` | `entries/react-dom.js`: React DOM root exports | `react` and its subpaths |
| `tonic` | `entries/tonic.js`: Tonic UI, Emotion, ordinary dependencies | React family |

Keep the two React entries separate: React and React DOM each need a `default`
export, and the local map sends `react`, `react-dom/client`, and the JSX
runtimes to the combined entry. Map only the application dependencies you
import; direct Emotion or sibling Tonic UI package imports need their own CDN and
local mappings.

### Manifest sources

[`scripts/build.mjs`](https://github.com/trendmicro-frontend/tonic-ui/tree/main/examples/cdn-with-fallback/scripts/build.mjs)
writes `dist/runtime-manifest.json` with both candidates per family:

| Field | What to inspect or change |
| :--- | :--- |
| `groups` | One group per npm package family: `react`, `react-dom`, `tonic-ui`. The `@`-scoped family renders without the `@` so every key stays a valid `data-*` attribute name. |
| `groups.<name>.cdn` | CDN mappings and probes for the family |
| `groups.<name>.local` | Local mappings and probes for the family |
| `shared.imports` | Generated Emotion mappings for the Tonic UI CDN source |
| `apps.app` | Application entry and CSS assets |
| `versions` | Installed versions used to generate CDN URLs |

The bootstrap selects `cdn` unless the group is forced local, probes it, and
reloads with the group forced local if the probe fails. The basic example is
the same bootstrap with `local` set to `null`, so a CDN failure ends startup
instead of reloading. Edit `groups.*.cdn.imports` in the generated manifest
for a development check; the dev server reloads when it changes. Builds
overwrite the file, so make permanent URL changes in `scripts/build.mjs`.

### Inspector scenario layer

The inspector frame loads the same shared bootstrap, which stays scenario-free.
[`public/inspector-bootstrap.js`](https://github.com/trendmicro-frontend/tonic-ui/tree/main/examples/cdn-with-fallback/public/inspector-bootstrap.js)
sits between the manifest and the bootstrap: it applies the selected scenario
as a manifest mutation (a missing module URL for a failing family, or
`cdn: null` to select local) and presents the bootstrap's structured `onStatus`
events as the load log and shell progress. The application document has no
scenario layer; it lets the bootstrap report events to the console.

## Build and deploy

From the example directory:

```bash
npm run build
npm run preview
```

`npm run build:inspector` adds the inspector files to the same output; the
docs build runs the same script with a different output directory.

Repeat the mounted-application and local-only checks in preview. Deploy the
complete `dist/` directory: document, bootstrap, manifest, application, and
all runtime assets. Fallback files must remain available without the CDN.

The build prefers the published Tonic UI standalone artifact (the `raw.esm.sh`
tarball file) and probes it: when the published package does not expose the
artifact, or the build is offline, the manifest selects the esm.sh standalone
build instead, and the generated Emotion mappings follow the selected source. A
CDN failure at runtime still falls back to the local source. The raw artifact
leaves React and Emotion external, so `scripts/emotion-redirects.mjs` produces
its mappings, while the local Tonic UI bundle includes Emotion and ordinary
dependencies separately.

## Troubleshooting

### Invalid hook calls or missing React exports

Keep matching React/React DOM versions, both source mappings, the external
rules, and the named-export plugin. Check for eager app imports or dependency
optimizer settings that bypass the bootstrap's selected runtime.

### Components render without styles

Keep the generated Emotion mappings. The raw artifact imports
`@emotion/react`, `@emotion/react/jsx-runtime`, `@emotion/styled/base`, and
`@emotion/is-prop-valid`; map all four and their CDN builds' absolute range
URLs to pinned entries. For example, `@emotion/styled` can request
`/@emotion/react@^11.0.0-rc.0?external=react&target=es2022`, which the bare
`@emotion/react` key does not cover. The peer range's `-rc.0` does not mean a
prerelease was installed. Missing a key can leave `Box p="4x"` at
`padding: 0px` instead of `16px` without an error. Reuse
`scripts/emotion-redirects.mjs` rather than hand-maintaining these keys.

### Tonic UI CDN failure or timeout

Use the inspector's selected sources, load log, and manifest section. Cold
builds can exceed the eight-second budget. Inspector Retry starts a new
runtime frame; in the example app, remove `__local` and `__failed` from the
URL to retry the CDN. Root pins do not necessarily pin every CDN-supplied
transitive dependency.

### Local files fail or the application does not mount

Check the complete deployment and manifest-relative asset URLs. Local, CSS,
application, and mount errors remain startup errors rather than causing a
retry loop. This example covers client-side startup, not SSR, later
lazy-import recovery, or arbitrary runtime exceptions.
